The RBAC pattern: one matrix, two readers

Manideep Daram, 2026-11-15 — Full Stack Developer, Hyderabad · portfolio

TL;DR. Role-based access control is not "hide the button." It is: one permissions matrix, read in two places — the UI decides what to render, and every API route decides what to allow. If only one of those two reads, the app leaks. This is how both my apps do it, with the actual code.

The matrix, straight from the source

DocVault's src/lib/permissions.ts is the entire authorization model in one file:

export type Permission =
  | 'doc:read'
  | 'doc:create'
  | 'doc:upload'
  | 'doc:review'
  | 'doc:delete';

const MATRIX: Record<Role, readonly Permission[]> = {
  viewer:   ['doc:read'],
  reviewer: ['doc:read', 'doc:review', 'doc:upload'],
  admin:    ['doc:read', 'doc:create', 'doc:upload', 'doc:review', 'doc:delete'],
};

export const can = (role: Role, permission: Permission): boolean => {
  const granted: readonly Permission[] | undefined = MATRIX[role];
  return granted ? granted.includes(permission) : false;
};

Two properties matter more than the shape:

  • Fail-closed. A role the matrix does not know — say, a tampered session cookie carrying role: "superadmin" — gets zero permissions instead of an exception. The default branch grants nothing.
  • One source. The UI and the server do not each maintain a list. Add a permission to the matrix and both readers see it in the same commit.

Reader one: the UI renders from the matrix

<RoleGate> wraps the controls a role shouldn't see. A viewer literally never renders the create button:

// The shape of it — gated, not just styled-disabled
<RoleGate allow="doc:create">
  <CreateButton onClick={…} />
</RoleGate>

This is UX. It tells a well-meaning user "this isn't yours to press." It tells a malicious one exactly nothing, because they are never required to go through it — which is why reader two exists.

Reader two: every route handler checks before it acts

The list endpoint verifies read access even though every role has it — the comment in src/app/api/documents/route.ts says why: "the UI is not the security boundary." The create endpoint is stricter:

const user = await getCurrentUser();
if (!user) return 401('Sign in to continue');

if (!can(user.role, 'doc:create')) {
  return 403('Only an admin can create documents');
}

Authentication is separate and happens first: no session, 401. The session cookie is httpOnly and sameSite=lax, so client-side script cannot read it and cross-site posts cannot ride it. Note the failure taxonomy is deliberate: 401 when we don't know you, 403 when we know you and you still may not — same wording to the caller as "unknown role," never more information than the refusal requires.

Honesty box: what this demo is and isn't

  • DocVault signs in with published demo logins (admin/admin, reviewer/reviewer, viewer/viewer) printed on the login page by design — so a reviewer can try each role in under a minute. There is no real account behind them.
  • The store is an in-memory mock database, not Postgres. The authorization path is the point of the project: the matrix, the gate, the 403. Swapping mockDb for a repository layer keeps the handlers unchanged.
  • Sessions are 8 hours, stateless — no refresh, no revocation list. That is the documented trade-off of the demo, not an oversight.

TaskFlow does the same thing with two different roles

TaskFlow splits access control into two halves. The coarse half is middleware:

export function requireRole(...roles: Role[]) {
  return (req, res, next) => {
    if (!req.userRole || !roles.includes(req.userRole)) {
      res.status(403).json({ error: 'Your role cannot do that' });
      return;
    }
    next();
  };
}

That answers "is this kind of person allowed here at all?" The fine half lives in the service layer, which is where the rules that are about relationships live — for example, from services/projectService.ts:

  • An admin sees and may delete every project.
  • A member sees the projects they created and the ones they have a task assigned in — so an assignment never becomes invisible.
  • A member may change only the projects they created; only an admin can delete a project at all. Members archive; they don't destroy other people's work.

The role travels inside the JWT and is handed to the service as an argument; the relationship questions (did you create this? are you assigned to it?) hit the database, because they are facts, not claims. That division keeps the token cheap and the rules honest.

What this buys you in a review

Someone auditing the codebase asks "where is the permission check?" and gets one file, one function, and 15 tests around can() and <RoleGate>. Not a grep across eleven components for if (role === — one grep, one answer.

FAQ

Is the permission check client-side only? No. The UI branch is cosmetic; the refusal that counts comes from the route handler (DocVault) or the service layer (TaskFlow).

What about JWT? JWT proves identity and carries the role claim. Anything about scope — which project, which document — is decided by querying data server-side. Tokens expire in seven days (TaskFlow) or eight hours (DocVault).

Why not hide buttons and stop there? Because curl -X DELETE api.example.com/projects/7 does not see your buttons.
