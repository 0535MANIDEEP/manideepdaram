How I keep two apps green on every push

Manideep Daram, 2026-11-15 — Full Stack Developer, Hyderabad · portfolio

TL;DR. TaskFlow runs 44 tests and DocVault runs 15 on every push and pull request — typecheck, unit/integration tests, production build. TaskFlow's tests run against an in-memory Postgres (pg-mem), so CI needs no database service and still executes the real SQL. Both repos also carry an ambient PR review Action that flags the mistakes tests don't: committed secrets, naked TODOs and missing tests.

The pipeline, in the order it fails

TaskFlow's .github/workflows/ci.yml is deliberately boring:

timeout-minutes: 10

steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with: { node-version: 24, cache: npm }
  - run: npm ci
  - run: npm run typecheck
  - run: npm test        # vitest, DB_DRIVER=memory
  - run: npm run build

Three design decisions are doing the work:

  • npm ci, never npm install. The lockfile is the claim; CI verifies it. If the lockfile is stale, the build fails loudly instead of resolving a different tree silently.
  • Typecheck is a separate step from tests. It catches the class of error tests never reach, and it fails fast.
  • Timeout 10 minutes. A hung job is worse than a red one — it blocks merges and teaches humans to ignore the badge. If it ever hits ten minutes, something is stuck, not slow.

Why pg-mem instead of a service container

TaskFlow's schema is real Postgres: foreign keys, cascade deletes, CHECK constraints. Running that in CI would normally mean a service container or a Docker layer. The trade-off I chose instead: pg-mem loads as if it were pg, and every query the suite executes is the same SQL the app runs in production. What pg-mem is not: a 100% faithful Postgres. Complex extensions and some edge semantics don't implement. That's acceptable for the authorization and validation rules the suite covers — and the reason the testing story documents its limit rather than claiming "full Postgres compatibility."

DocVault is simpler by comparison: no database at all. Its 15 tests pin down can() over the full role × permission grid, <RoleGate>'s rendered output under react-dom/server, schema validation, and the demo-account flow.

What the tests deliberately do not test

  • Pixels. No Playwright in CI. Both apps are small enough to eyeball and there is no design system to regress against.
  • The live deployment. Vercel and GitHub Pages own that failure domain; CI gates the repo, not the CDN.
  • Load. Free tiers have hard limits and pretending otherwise helps nobody.

The ambient PR reviewer

Tests catch behavior. They do not catch the classic human slips, so both repos run a second workflow on every PR that leaves a single informational comment:

  • Hard-coded credential patterns (ghp_…, sk-…, AWS access keys, private-key headers) — merge-blocking flag.
  • Naked TODO/FIXME without an issue reference.
  • Source changed with zero test-file changes in the same diff.
  • New console.* calls in non-test source.
  • .env-style files carrying long values instead of placeholders.
  • Any source file grown past 300 lines — a smell, not a blocker.

It is advisory, never a gate: a red comment does not stop merge. It exists so a future reviewer — or a future me — asks "why?" out loud. When it ran against a deliberately trivial .env.example PR (#1), the whole run took 8 seconds and it posted: no credentials, no naked TODOs, no source changes requiring tests.

The honest limits

  • pg-mem passing is weaker evidence than real Postgres passing. It proves the app runs the SQL; it does not prove Postgres-specific behavior end to end. TaskFlow's .env.example + Neon free tier cover the real-database path for local development.
  • Green CI does not mean the app works for a user. It means the contract the tests describe still holds.
  • Coverage is not measured as a percentage gate. I test the rules that must not break — authorization, validation, the permission matrix — not for a number.
